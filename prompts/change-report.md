# Generate Change Report

> **OpenCode → Pi note (ported skill).** Term mapping for the body below:
> - OpenCode **question tool** → Pi has no separate tool; **ask the user clarifying questions directly in your response.**
> - **scout sub-agent** / **task tool** (`subagent_type: "scout"`) → Pi's builtin **`scout`** agent launched via the **`subagent(...)`** tool. Fork three in parallel with `subagent({ tasks: [ { agent: "scout", task: "..." }, ... ], concurrency: 3 })`. "Gemini 3.5 Flash" = the cheap fast model in the source skill; the audit just needs cheap parallel reviewers.
> - **edit tool** → Pi's `edit`. **read tool with offset/limit** exists in Pi as-is. **write tool** → Pi's `write`.
> - Report output uses the convention `<git_root>/.opencode-cache/YYYY-MM-DD-HH/`; keep it or choose your own report directory. The pandoc styling CSS lives at `/home/zlare/.pi/agent/prompts/change-report.css` (see the CSS section at the end of this prompt).

**Change-report scope:** ${ARGUMENTS:-<scope — "this branch" | "last N commits" | "since &lt;ref&gt;" | "&lt;A&gt;..&lt;B&gt;" | "all changes">}

Let's do a multi-file approach. Instead of one long report file, the model will create one markdown artifact per commit (forget about the ROADMAP for now. Commits will match up with ROADMAP tasks anyway, so we can just ask the model to use the roadmap as a reference document and rely on diffs).

The model will:
1. For each commit, pipe its diff into a *separate file* in the `YYYY-MM-DD-HH` folder, with the commit hash as the filename and as a markdown file (xxxxxx.md).
2. Then, create a footnotes.md file.
3. For each commit, work only off of its specific file, and pretend the others don't exist. Edit the file, breaking up the diff into chunks (with fenced codeblocks) and a conversational-style explanation of choices based on ROADMAP. Use footnotes, and put the footnotes in footnotes.md.
4. Finish each individual commit hash file, and keep the footnotes.md as a running accumulation of all footnotes.
5. Concatenate the files together using a shell command, to create the full report, with commits in time order so that later commits are later sections, and ending with the footnotes section.
6. DO NOT read that file. Generate the HTML with the complete file using pandoc, then send the HTML file's location to the user and tell them the report is ready.

## Goal

Produce a comprehensive, self-contained change report written in the style of a technical blog post or deep-dive article. The report documents every code change, every agent decision point, and every user-authorized rationale for a given scope of git history, but does so as flowing narrative prose — not as bullet-pointed lists, structured ledgers, or label-value pairs.

The final result must include both:

1. A markdown file at `<git_root>/.opencode-cache/reports/YYYY-MM-DD-HH/report.md` containing the full report.
2. An HTML sidecar at the same path with a `.html` extension, generated by invoking `pandoc` on the markdown file.

The HTML file is a rendered artifact only. It must never be edited directly. The intended workflow is: edit the markdown, then re-run pandoc to re-render the HTML.

## Writing style contract

The report must read like an indie tech-blog deep-dive — the kind of opinionated, knowing, slightly sry engineering write-up you would find on a detailed pull-request review or a personal blog. The voice is conversational but precise: willing to call out awkward choices without being cruel, honest about tradeoffs, never a victory lap. It is anchored in vivid, concrete detail — function names, line counts, config keys, exact error messages, renamed symbols — and each commit section opens with a clear hook stating what the change actually does, carries narrative momentum through the diff, and explains decisions as it goes rather than listing them. Think strong verbs, short decisive sentences mixed with longer analytical ones, the occasional dry aside, and zero corporate filler. The reader should be able to sit down and read the report from top to bottom as a continuous story about what changed, why it changed, how it was implemented, and what tradeoffs were made.

This means:

- Write in complete paragraphs, not fragments. Every section is prose that flows into the next.
- Do not use bullet-pointed lists, `**Label**: value` pairs, or structured ledgers to present changes, decisions, or behavior impacts. These are forbidden output formats. The only exception is the report's top metadata block (see "Report header" below), which uses a simple key-value format for machine-readable facts.
- Code blocks are embedded inline within the narrative. Each code block is introduced by a paragraph (or several) that explains what the code does, why it was written this way, and what decisions it embodies. The code block is part of the sentence flow — the surrounding prose leads into it naturally, and the prose after it may continue the discussion.
- Decision points are discussed as part of the narrative, not extracted into a separate list. When describing a piece of code, the narrative should explain the choice that was made, why it was made, and what alternatives were rejected. This discussion happens in the same paragraph or paragraphs that present the code.
- Behavior changes are described in context. When a piece of code changes existing behavior, the narrative explains what the previous behavior was, what the new behavior is, and why the change was authorized — all as flowing prose, not as a ledger entry.
- Tests are discussed as part of the implementation story. The narrative explains what was tested, how, and what the test proves, woven into the discussion of the code it covers.
- In Mode A, Q&A citations are referenced as footnotes within the prose. The footnote marker appears naturally in the sentence that discusses the authorized decision. The footnote itself contains the verbatim user quote.

The report should have headers to organize sections (by task in Mode A, by commit in Mode B), but within each section, the content is narrative prose with embedded code blocks — not sub-sectioned lists.

### Voice: detached analyst, never owner

The writer is an observer and analyst of the code — never its author or owner, even when documenting commits the agent itself may have produced in a prior session. The report is written from the outside looking in. This is non-negotiable and applies to every commit section.

- **No first-person ownership of the code or the project.** Forbidden phrasings include "I implemented X", "I added a function that...", "I decided to", "my approach", "we built". The agent is documenting the diff, not claiming credit for it, and must never present the repo's project as its own handiwork.
- **Describe changes in the third person, as things the commit does.** Prefer "The commit introduces a decorator that deep-copies inputs", "This change replaces the JSON writer with an atomic write-and-rename", "The new node halts execution and returns a resume token". The subject of every sentence is the code or the commit — never the writer.
- **First person is reserved for the act of reading the diff, and even then, prefer the impersonal.** "The diff reveals..." is better than "I can see...". The default voice is third-person, observational, analytical.
- **The code is the hero of the story.** Decisions are discussed as properties of the code ("the decorator enforces immutability because shared mutable state is the largest source of non-determinism"), not as personal choices ("I chose immutability because...").

### Example voice

The commit-section prose below illustrates the target voice — indie-blog personality, vivid concrete detail, detached analytical stance, and zero ownership claims. Every run should sound like this.

> The commit's central addition is a decorator that enforces immutability at the node boundary. The motivation is straightforward and worth stating plainly: shared mutable state between nodes is the single largest source of non-deterministic workflow bugs, and catching mutation at the decorator level turns a whole class of runtime surprises into guarantees that hold before the first token is spent.
>
> ```python
> def autom_node(fn):
>     @wraps(fn)
>     def wrapped(*args, **kwargs):
>         args = deepcopy(args)
>         ...
> ```
>
> An opt-out escape hatch ships alongside it for the cases where the copy cost is provably unacceptable, which keeps the default safe without painting performance-sensitive callers into a corner.

Note what the example does not do: it never says "I added this decorator" or "I chose immutability". The subject is always the code and the commit, never the writer, and the local project is described as a system under analysis rather than a personal creation.

## Core rules

1. **ALL code is included.** Every line of code that was added or modified within the report scope must appear in the report as a fenced code block. No truncation, no ellipsis, no "rest of file unchanged" shortcuts. This is non-negotiable.

2. **Two modes, determined by ROADMAP.md presence.** The report structure branches based on whether a `ROADMAP.md` exists at the git root. The mode determines the section organization and whether Q&A citations are used.

3. **Decision points are woven into the narrative.** Every point where the implementing agent made a choice — naming, structure, algorithm, API surface, error handling, file placement, test strategy — must be discussed in the prose with rationale. The reader should understand not just what was done but why.

4. **Pandoc is mandatory.** After the markdown is written, the agent must invoke `pandoc` to produce the HTML sidecar. If pandoc is not installed, the agent must report this and stop — do not produce HTML by any other means.

5. **The HTML is never the source of truth.** If the user asks to update the report, edit the markdown and re-run pandoc. Never edit the HTML directly.

## Entrypoint

When this skill is invoked, perform the following operations, in the following order.

First, create `<git_root>/.opencode-cache/reports/YYYY-MM-DD-HH` if it does not exist.

Then, proceed to the scope detection phase.

### Scope detection

Before gathering any changes, determine the scope of the report from the user's request.

#### Common scope patterns

| User request pattern | Git command |
|---|---|
| "summarize changes on this branch" | `git log $(git merge-base HEAD main)..HEAD` (fallback to `master` if `main` does not exist. `dev` is also a common possibility) |
| "summarize last N commits" | `git log -n N` |
| "summarize changes since \<ref\>" | `git log <ref>..HEAD` |
| "summarize changes between A and B" | `git log A..B` |
| "summarize all changes" | `git log` (full history, warn the user if this is very large) |

If the user's request does not match any pattern, use the question tool to clarify the scope before proceeding. *(Pi note: "use the question tool" = ask the user the clarifying questions directly in your response.)*

### Scope verification

After determining the scope, run the git command and verify that commits exist. If no commits match the scope, inform the user and stop.

If everything is good, move on to the report generation phase.

## Report Generation

First, check whether `ROADMAP.md` exists. If it does, read it into context and use it as a supplementary source for generating the report. The roadmap is always supplementary; diffs are AUTHORITATIVE and should be used as the source of truth. If the roadmap is not up to date, prefer the diff version and note the discrepancy in the report.

Then, run the relevant git commands to dump the diffs to each file. For each commit that is being analyzed, dump its commit message and the diff to `<git_root>/.opencode-cache/YYYY-MM-DD-HH/<commit_hash>.md`. Only after each relevant commit has been dumped do you proceed from this step.

Under NO CIRCUMSTANCES can you ever use any other command to write diffs manually. Diffs must be dumped using `git diff` and other git commands ONLY. This prevents the diff from passing through the model and potentially being hallucinated, and also makes sure that no parts of the diff are missing. If an individual diff is too large, you may use shell commands to break it up across multiple files and work on one at a time at your own discretion, but writing diffs manually is PROHIBITED. Diffs MUST BE DUMPED to a file directly and then narrative added using the edit tool.

After this, create a `<git_root>/.opencode-cache/YYYY-MM-DD-HH/footnotes.md` file. This file will include footnotes for the report, which are citations to individual Q&A sessions from `ROADMAP.md`. If `ROADMAP.md` is not present, then the `footnotes.md` file will simply be empty; this is expected and intended.

Once the status is prepped, alert the user, and then move to the Commit Report Generation sub-step. DO NOT read the diff files.

### Commit Report Generation

During the Commit Report Generation sub-step, you will generate a report only for a specific commit. Pretend that no other commits exist, and because the diff is already authoritative, write the diff explanation using ONLY the code shown in the diff and only by reading the exact files mentioned in the diff. You are FORBIDDEN from reading files that are not mentioned in the diff, and even when reading the files in the repo, you should conservatively read in chunks only the relevant line segments surrounding the lines in the diff. This is both to conserve context window and also because files on disk may have been changed by later commits, but those changes should not be mentioned in this commit due to chronological ordering.

Only during this stage, you are allowed to read the ONE diff file related to the commit that is currently being prepared. Do not read the others until you reach that stage, as it wastes context window and that information is not relevant to generating the report.

No sub-agents, no delegation, no parallelism. FOCUS! Because we are operating under a tight context window, we read the absolute minimal amount of information necessary to generate the summary just for one commit, and then move to the next one.

In order to preserve the integrity of the diff file and make sure you didn't miss anything, you are not allowed to use the write tool for this operation. You are only allowed to use the edit tool to generate this report, and you CAN NOT DELETE any diff lines that contain code. The non-code header lines — the `git diff` command invocation, `diff --git ...`, `index ...`, and `+++`/`---` file markers — are not code and may be removed, but only if replaced with a more user-readable comment at the top of the block indicating the file and line range that the diff corresponds to.

Diff formatting should not contain the raw command used to produce that diff. Replace the diff header with a readable comment naming the file and line range it corresponds to.

Also, in standard conversational style, there should be AT MOST two to three sentences of explanation per codeblock, and each codeblock should be around 5 to 10 lines (though more is possible if it corresponds to a single functional unit). However, if the function of code in a codeblock can't be adequately explained in three short, simple sentences, it should be split into more codeblocks.

Commit report formatting should have the following elements:
- A h2 markdown header (##) which specifies a summary of the commit message
- A h3 Summary header, under which a short summary of changes is specified (bullet-points okay)
- A h3 Changelog header, under which the diff is placed in a fenced codeblock.
  - Interspersed between the lines of the diff, insert explanatory sentences (outside the codeblock, so we want multiple codeblocks, not comments within the codeblock) that explains the reasoning behind changes or what certain changes do. Add footnotes wherever relevant, and put those footnotes in the `footnotes.md` file.
  - During the process of adding commentary to the diffs to explain decisions or code, deleting diff lines that contain code is ABSOLUTELY PROHIBITED. All changed code must be presented to the user in full, even if the changes are formatter changes or even just stray characters or empty lines. The only lines that may be removed are the non-code diff header/command lines (`diff --git`, `index`, `+++`/`---` markers, the `git diff` invocation), and those must be replaced with the readable file-and-line-range comment described above.
- Every intermediate file (each per-commit `<hash>.md` and `footnotes.md`) MUST end with a single trailing blank line. Without it, concatenation fuses the last line of one section into the header of the next and produces broken, invalid markdown.

#### Footnote citations

If `ROADMAP.md` is present, use markdown footnotes to cite Q&A sessions from its `# Architecture Contract` section.

Footnote format:

```markdown
[^1]: Q&A Session YYYY-MM-DD HH:MM — "<exact quote from the user's answer that authorizes this decision>"
```

Once the commit report is generated, move to the next commit. If all commits are handled, move to the Full Report Generation sub-step.

### Full Report Generation

During this step, the full report is synthesized. Concatenate each markdown file together, in chronological order, with `footnotes.md` at the very end, to create `<git_root>/.opencode-cache/YYYY-MM-DD-HH/report.md`. Each intermediate file already ends with a trailing blank line, so the sections join cleanly — verify the concatenation command preserves those separators rather than stripping trailing newlines.

Do NOT render yet. The report was assembled commit-by-commit in isolation, so contradictions can slip in between sections — one commit's commentary may claim a mechanism needs no restart while another's says the user restarts to load it. Before invoking `pandoc`, the assembled `report.md` must pass the contradiction and citation audit below. Only once every issue it surfaces is resolved may pandoc render the HTML sidecar; after a successful render, alert the user that the report is ready and send the file path.

#### Contradiction and citation audit

Fork **three** scout sub-agents in parallel to critically review the assembled `report.md`. Scout sub-agents run on the cheap fast model, so three independent reviewers cost negligible time and money and catch far more than one. Launch all three concurrently in a single message. (This does not violate the "no sub-agents" rule — that restriction applies only to the per-commit generation step; the audit is a separate phase that runs on the finished `report.md`.)

Frame the review request neutrally. LLM reviewers are sycophantic: any hint that the file is "ours", "the article I wrote", or "our report" makes the reviewer pull its punches. The driving model must NOT use possessive or affiliated language when addressing the sub-agents — frame the document as an external artifact under review, nothing more. Hand each sub-agent exactly this prompt (substituting the absolute path to `report.md`):

> You are a dedicated, critical article reviewer. Read the file at `<absolute_path_to_report.md>` in full. Your job is to find flaws, not to praise. Report two things, and only these two things:
>
> 1. Internal contradictions. Any place where the document asserts something that conflicts with another assertion elsewhere in the same document — directly or by necessary implication. For each contradiction, quote the exact conflicting passages (both sides), state where each appears, and explain how they conflict.
> 2. Unsubstantiated claims lacking a footnote citation. Any statement of fact or authorized decision rationale that is presented without a supporting footnote. For each, quote the claim, state where it appears, and note that it lacks a supporting footnote. Footnotes are expected wherever a decision is attributed to a `ROADMAP.md` Q&A session; if no `ROADMAP.md` is present, report this category as empty.
>
> Be ruthless and specific. Quote exact text. If a category is empty, say so explicitly. Do not summarize the article's merits; list defects only.

When all three return, take the **union** of their findings — address everything any single agent raised. Do not require multiple reviewers to agree before fixing; one sharp-eyed agent catching a real defect is enough. For each finding:

- **Contradiction**: resolve it by editing `report.md`. Determine which side is correct against the diff (authoritative) and the `ROADMAP.md` if present, then rewrite so the document is self-consistent. Re-read the surrounding paragraphs after each fix to confirm no new contradiction was introduced.
- **Unsubstantiated claim lacking a footnote**: either remove it, or remedy it by adding the supporting footnote citing the `ROADMAP.md` Q&A session that authorizes it. If the claim cannot be supported, cut it.

Apply every fix to `report.md` directly with the edit tool. This is a remediation pass, not a re-run of diff analysis. Only after every raised issue is addressed may pandoc render the HTML.

The driving model is NOT ALLOWED to read the full `report.md` into its own context — the assembled file is large and streaming it whole wastes the context window the per-commit isolation was designed to protect. It may read **targeted sections only** (via the read tool with `offset`/`limit`) to inspect the exact passages a sub-agent reviewer flagged, then edit just those parts. Never read the whole assembled file end to end.

#### Pandoc Details

Use the following command to invoke `pandoc`:

```bash
pandoc -s --embed-resources --standalone --css="/home/zlare/.pi/agent/prompts/change-report.css" --toc --toc-depth=3 --metadata title="Change Report: <repo name>" "<md_file>" -o "<html_file>"
```

Where:
- `<md_file>` is the absolute path to the markdown file.
- `<html_file>` is the same path with a `.html` extension instead of `.md`.
- `<repo name>` is the repository name (from the git root directory name).
- `--embed-resources` inlines the CSS (and any linked assets) directly into the HTML so the sidecar is fully self-contained.
- The CSS file lives at `/home/zlare/.pi/agent/prompts/change-report.css` and applies an Everforest Light Medium theme.

### Post-render verification

After running pandoc, verify the HTML file was created:

```bash
test -f "<html_file>" && echo "ok" || echo "failed"
```

If the render failed, inform the user of the pandoc error output and the markdown file location.
