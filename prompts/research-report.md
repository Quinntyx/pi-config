# Generate Research Report

> **OpenCode → Pi note (ported skill).** Term mapping for the body below:
> - **scout sub-agent** / **task tool** (`subagent_type: "scout"`) → Pi's builtin **`scout`** agent launched via the **`subagent(...)`** tool. Fork up to 10 per round with a single `subagent({ tasks: [ { agent: "scout", task: "..." }, ... ], concurrency: 10 })` call.
> - **webfetch** → Pi's web-access tool (e.g. the `researcher` builtin subagent, or a web fetch tool if available). "Gemini quota" refers to the source skill's cheap sub-agent model; treat it as "the sub-agent round failed / quota exhausted."
> - **edit tool** → Pi's `edit`.
> - Report output uses the convention `<git_root>/.opencode-cache/reports/YYYY-MM-DD-HH/`; keep it or choose your own report directory. The pandoc styling CSS lives at `/home/zlare/.pi/agent/prompts/research-report.css` (see the CSS section at the end of this prompt).

**Research topic:** ${ARGUMENTS:-<topic, library, URL, or question to investigate in depth>}

This skill does multi-round sub-agent research, not git-diff analysis. The model forks scout sub-agents to gather precise factual data, cross-references their outputs across rounds to filter out hallucinations, discards anything uncorroborated, and then writes the surviving facts up as a narrative technical article.

The model will:
1. Fork up to 10 scout sub-agents per round, each with a well-defined, bounded research task.
2. Read the results back, extract exact factual data points, and write them to a per-round file.
3. Run another round of sub-agents with the same (or slightly modified) prompts.
4. Cross-reference rounds: facts repeated by multiple independent passes are treated as corroborated.
5. Loop rounds until enough precise, corroborated data exists to answer the user's query.
6. Discard all data not corroborated by at least 2 sub-agent passes. Verify a small number of critical data points (CVE numbers, issue numbers) with direct web fetches.
7. Write the surviving data as a narrative article, section by section, into per-section files plus a `footnotes.md`.
8. Concatenate the section files together with `footnotes.md` at the end to create `report.md`.
9. DO NOT read `report.md` back. Generate the HTML with pandoc, then send the HTML file's location to the user and tell them the report is ready.

## Goal

Produce a comprehensive, self-contained research report written in the style of a technical blog post or deep-dive article. The report presents verified findings from multi-round sub-agent research, cross-referenced to filter hallucinations, with every claim backed by corroboration or direct verification — but delivered as flowing narrative prose, not as bullet-pointed lists, structured ledgers, or label-value pairs.

The final result must include both:

1. A markdown file at `<git_root>/.opencode-cache/reports/YYYY-MM-DD-HH/report.md` containing the full report.
2. An HTML sidecar at the same path with a `.html` extension, generated by invoking `pandoc` on the markdown file.

The HTML file is a rendered artifact only. It must never be edited directly. The intended workflow is: edit the markdown, then re-run pandoc to re-render the HTML.

## Writing style contract

The report must read like an indie tech-blog deep-dive — the kind of opinionated, knowing, slightly wry engineering write-up you would find on a personal blog run by someone who has clearly spent too long in the trenches with the subject. The voice is conversational but precise: willing to call out bad design without being cruel, honest about tradeoffs, never a sales pitch. It is anchored in vivid, concrete detail — CVE numbers, dollar figures, star counts, exact dates, direct quotes — and it opens with a punchy hook, keeps narrative momentum through every section, and closes with a clear-eyed verdict rather than a hedge. Think strong verbs, short decisive sentences mixed with longer analytical ones, the occasional dry aside, and zero corporate filler. The reader should be able to sit down and read the report from top to bottom as a continuous story about what was investigated, what was found, how the findings fit together, and what tradeoffs or caveats apply.

This means:

- Write in complete paragraphs, not fragments. Every section is prose that flows into the next.
- Do not use bullet-pointed lists, `**Label**: value` pairs, or structured ledgers to present findings, comparisons, or conclusions. These are forbidden output formats. The only exception is the report's top metadata block (see "Report header" below), which uses a simple key-value format for machine-readable facts.
- Code blocks, command examples, and data tables are embedded inline within the narrative. Each block is introduced by a paragraph (or several) that explains what it shows, why it matters, and what it proves. The block is part of the sentence flow — the surrounding prose leads into it naturally, and the prose after it may continue the discussion.
- Findings are discussed as part of the narrative, not extracted into a separate list. When presenting a fact, the narrative should explain the context, the evidence, and any caveats. This discussion happens in the same paragraph or paragraphs that present the fact.
- Comparisons are described in context. When two approaches, tools, or data points are compared, the narrative explains what each one is, how they differ, and why the difference matters — all as flowing prose, not as a ledger entry.
- Caveats and limitations are discussed as part of the story. The narrative explains what is uncertain, what could not be verified, and how confident the reader should be, woven into the discussion of the relevant finding.
- Source citations are referenced as footnotes within the prose. The footnote marker appears naturally in the sentence that presents the corroborated fact. The footnote itself contains the source reference and the corroboration count.

The report should have headers to organize sections (by research sub-topic), but within each section, the content is narrative prose with embedded code blocks and tables — not sub-sectioned lists.

### Voice: detached analyst, never owner

The writer is an observer and analyst — never a participant, author, or owner of the subject under study, and never the author or owner of any project that lives in the repo. The report is written from the outside looking in. This is non-negotiable and applies to every paragraph.

- **No first-person ownership of the repo's own project.** The agent did not build the project that lives in the repo and must never claim to have. Forbidden phrasings include "I built X to do Y", "I've been working on Z", "my framework", "our approach", "we designed". These read as credit-claiming and bias the report toward presenting the repo's project as the end-all-be-all solution.
- **Reference the repo's own project in the third person, as one data point among several.** When the report cites a local `ROADMAP.md`, README, or source file to compare against the researched subject, frame it as a reference point — never as the protagonist or the implied winner. Prefer "Compared to OpenClaw, autom does X" or "Where OpenClaw relies on dynamic schemas, the repo's approach leans on static typing" — never "I built autom to fix this."
- **First person is reserved for the act of investigation, and even then, prefer the impersonal.** "Reading the source turned up..." is acceptable; "the source reveals..." is better. The default voice is third-person, observational, analytical.
- **Analyze every subject at the same level — no bias toward either side.** When the report compares a researched topic against the repo's own project (or against any other subject), treat them as peers. Do not stack the framing to favor one over the other. Weigh each one's strengths and weaknesses even-handedly, and let the evidence decide the verdict — which may be a tie, a split decision, or an outright "it depends." Neither the researched topic nor the repo's project is the protagonist by default; neither is assumed to be the better solution.

### Example voice

The prose below illustrates the target voice — indie-blog personality, vivid concrete detail, detached analytical stance, and zero ownership claims about any local project. Every run should sound like this.

A punchy, knowing opening hook:

> There's a particular kind of project that explodes on GitHub, accumulates a third of a million stars in seven months, and then immediately catches fire. OpenClaw is that project. It's a local-first AI assistant framework — an "operating system for agents" — that hit roughly 380k stars (global rank around #6) within about seven months of its November 2025 repository creation.[^1] It also shipped a CVSS 8.8 one-click remote code execution vulnerability,[^2] weathered a `$CLAWD` scam token that drained $16M, survived a 72-hour malware flood on its package registry, and bled users' API budgets dry through a heartbeat mechanism that nobody seemed to configure correctly.

The detached comparison voice when a local project enters the picture — note that it weighs both sides even-handedly and names the tradeoff honestly rather than crowning either one the winner:

> Where OpenClaw relies on runtime JSON-RPC tool schemas validated only at the gateway boundary, the repo's approach leans on statically typed Python handles checked before a single token is spent. The tradeoff is real and worth naming: OpenClaw buys flexibility and a richer out-of-the-box tool surface, while the local design buys determinism and an entire class of bugs that simply cannot occur.

Both examples keep the personality — the rhythm, the concrete numbers, the willingness to judge — while staying firmly in the detached analyst's chair.

## Core rules

1. Every fact in the report must be a precise, specific data point with a source. EXPLICIT = GOOD, VAGUE = BAD. Reject vague phrasing like "generally", "usually", "it is said that". If a fact cannot be stated precisely with a reference, it does not go in the report.

2. A single sub-agent returning a fact is not enough. A fact must appear in the outputs of at least two independent sub-agent passes (across rounds) to survive into the report. DISCARD EVERYTHING ELSE. This is the primary hallucination filter and is non-negotiable.

3. If the first round of 10 sub-agents fails, assume the sub-agent quota is exhausted. STOP IMMEDIATELY. DO NOT fall back to web fetches manually without sub-agents. The first round is the load-bearing pass; if it cannot run, the skill cannot produce a trustworthy report and must fail loudly rather than degrade into un-corroborated single-source research.

4. Direct verification is a scarce, surgical tool reserved for the most critical verifiable identifiers (CVE numbers, issue numbers, exact version strings) that were not corroborated by 3+ passes. NO MORE THAN 5 DIRECT web fetch CALLS. Research that needs more verification than this must go back through sub-agents to keep throughput high.

5. **Pandoc is mandatory.** After the markdown is written, the agent must invoke `pandoc` to produce the HTML sidecar. If pandoc is not installed, the agent must report this and stop — do not produce HTML by any other means.

6. **The HTML is never the source of truth.** If the user asks to update the report, edit the markdown and re-run pandoc. Never edit the HTML directly.

## Entrypoint

When this skill is invoked, perform the following operations, in the following order.

First, create `<git_root>/.opencode-cache/reports/YYYY-MM-DD-HH` if it does not exist.

Then, proceed to the Research Phase.

### Topic decomposition

Before forking any sub-agents, decompose the user's research query into up to 10 well-defined, bounded research tasks. Each task must be narrow enough that a single scout sub-agent can return precise, citable facts rather than a broad summary. Good tasks ask for exact data points: specific version numbers, CVE identifiers, issue numbers, API signatures, benchmark figures, dates, or direct quotes from documentation. Bad tasks ask for "an overview of" or "a summary of".

If the user's request is ambiguous about scope, use the question tool to clarify before decomposing. *(Pi note: "use the question tool" = ask the user the clarifying questions directly in your response.)*

Write the task list down. These tasks are the prompts for every round of sub-agents.

## Research Phase

The Research Phase gathers precise factual data through repeated, cross-referenced sub-agent passes. The goal is corroboration: the same fact, returned independently by multiple passes, is treated as verified.

### Round execution

For each round:

1. Fork up to 10 scout sub-agents in parallel (one per research task), using the `subagent(...)` tool with `agent: "scout"` (Pi's builtin scout). Each sub-agent gets its bounded task prompt. Launch them concurrently in a single message to maximize throughput.

2. If forking the sub-agents fails on the first round, assume sub-agent quota is exhausted. STOP IMMEDIATELY. DO NOT fall back to web fetch calls directly without sub-agents. The first round is mandatory; without it there is no corroboration baseline.

3. Read the results back from each sub-agent. Extract exact factual data points — version strings, identifiers, figures, dates, direct quotes, source URLs. Write the extracted facts for this round to `<git_root>/.opencode-cache/reports/YYYY-MM-DD-HH/round-N.md`. List each fact on its own line with its source so it can be tallied for corroboration.

4. Run another round of sub-agents with the exact same prompts (or slightly modified prompts that target the same data points from a different angle, to get independent corroboration rather than copied phrasing).

5. If a later round crashes (round 2 onward), do not worry — you already have at least one round of results. PROCEED TO THE WRITING PHASE with the data already gathered. Later-round failures are recoverable; only the first-round failure is fatal.

6. If the round succeeded, cross-reference its results against all previous rounds. A fact repeated by two or more independent passes is corroborated. A fact from a single pass only is uncorroborated and is a candidate for discard.

7. Loop: dispatch additional rounds with identical or slightly modified prompts to keep cross-referencing and to fill gaps in the precise factual data. Keep going until the corroborated data is sufficient to answer the user's query in full, with explicit data points and references throughout.

8. When you have enough precise, corroborated factual data to answer the user's query, proceed to the Writing Phase.

### Corroboration tally

Maintain a running tally as rounds complete. For each distinct fact, record how many independent passes returned it. The tally lives in `<git_root>/.opencode-cache/reports/YYYY-MM-DD-HH/corroboration.md` and is updated after every round. Facts with a tally of 2+ are eligible for the report. Facts with a tally of 1 are discarded unless rescued by direct verification in the Writing Phase.

## Writing Phase

The Writing Phase filters the gathered data and writes the surviving facts up as a narrative article.

### Verification and discard

1. Discard every fact whose corroboration tally is below 2. This is the hard filter.

2. For the small number of super-critical, verifiable identifiers that were NOT corroborated by 3+ passes — exact CVE numbers, issue numbers, commit hashes, version strings — make a direct web-fetch call yourself (no sub-agent) to verify the data point against its primary source. NO MORE THAN 5 SUCH CALLS. If a critical identifier cannot be verified within this budget, either send it back through another sub-agent round or drop it and note the gap in the report.

3. The surviving data set is the corpus for the report. Everything in it is either corroborated by 2+ passes or directly verified.

### Article writing

Take the surviving data points and write a technical indie-blog-style article. Follow the Writing style contract above: narrative prose, embedded code blocks and tables, findings discussed in context, no bullet ledgers. Crucially, follow the Voice rules — detached analyst, never owner. No first-person ownership of the repo's own project; the researched subject is the hero, the local project is at most a comparison foil, and every claim is made from the outside looking in.

Write the report section by section, one research sub-topic per section file, into `<git_root>/.opencode-cache/reports/YYYY-MM-DD-HH/<section-slug>.md`. This mirrors the multi-file discipline: each section is written in isolation, pretending the others do not exist, so the narrative for each sub-topic stays focused.

In standard conversational style, there should be at most two to three sentences of explanation per code block or data table, and each block should be around 5 to 10 lines (though more is possible if it corresponds to a single functional unit). If the function of a block cannot be adequately explained in three short, simple sentences, split it into more blocks.

Section formatting should have the following elements:
- An h2 markdown header (`##`) naming the research sub-topic.
- An h3 Summary header, under which a short summary of the section's findings is specified (bullet points okay here only because this is the summary block, not the narrative body).
- The narrative body: prose with embedded code blocks, command examples, and data tables, each introduced and explained by surrounding paragraphs. Add footnote markers wherever a corroborated fact is stated, and put the footnotes in `footnotes.md`.

#### Footnote citations

Use markdown footnotes to cite the sources that corroborate each fact. Every factual claim in the narrative carries a footnote marker.

Footnote format:

```markdown
[^1]: Source: <url or reference> — corroborated by N sub-agent passes
```

For directly verified identifiers (step 2 above), use:

```markdown
[^2]: Verified directly via <url> — primary source confirmation
```

### Full Report Generation

Once every section file is written, synthesize the full report. Concatenate the section files together, in a logical reading order, with `footnotes.md` at the very end, to create `<git_root>/.opencode-cache/reports/YYYY-MM-DD-HH/report.md`.

Do NOT render yet. The report was assembled from section files written in isolation, so contradictions can slip in between sections — one paragraph may claim a mechanism needs no restart while another says the user restarts to load it. Before invoking `pandoc`, the assembled `report.md` must pass the contradiction and citation audit below. Only once every issue it surfaces is resolved may pandoc render the HTML sidecar; after a successful render, alert the user that the report is ready and send the file path.

#### Contradiction and citation audit

Fork **three** scout sub-agents in parallel to critically review the assembled `report.md`. Scout sub-agents run on the cheap fast model, so three independent reviewers cost negligible time and money and catch far more than one. Launch all three concurrently in a single message.

Frame the review request neutrally. LLM reviewers are sycophantic: any hint that the file is "ours", "the article I wrote", or "our report" makes the reviewer pull its punches. The driving model must NOT use possessive or affiliated language when addressing the sub-agents — frame the document as an external artifact under review, nothing more. Hand each sub-agent exactly this prompt (substituting the absolute path to `report.md`):

> You are a dedicated, critical article reviewer. Read the file at `<absolute_path_to_report.md>` in full. Your job is to find flaws, not to praise. Report two things, and only these two things:
>
> 1. Internal contradictions. Any place where the document asserts something that conflicts with another assertion elsewhere in the same document — directly or by necessary implication. For each contradiction, quote the exact conflicting passages (both sides), state where each appears, and explain how they conflict.
> 2. Unsubstantiated factual claims. Any factual statement that is not backed by a footnote citation. For each, quote the claim, state where it appears, and note that it lacks a supporting footnote.
>
> Be ruthless and specific. Quote exact text. If a category is empty, say so explicitly. Do not summarize the article's merits; list defects only.

Note what the prompt does: it asks only "are there contradictions in this file" and "which factual claims lack footnotes", with no possessive framing and no invitation to be kind.

When all three return, take the **union** of their findings — address everything any single agent raised. Do not require multiple reviewers to agree before fixing; one sharp-eyed agent catching a real defect is enough. For each finding:

- **Contradiction**: resolve it by editing `report.md`. Determine which side is correct against the corroborated source data and the section files, then rewrite so the document is self-consistent. Re-read the surrounding paragraphs after each fix to confirm no new contradiction was introduced.
- **Unsubstantiated factual claim**: either remove it, or remedy it by adding a supporting footnote (re-verifying against a primary source if needed, staying within the direct web-fetch budget already established). If a claim cannot be supported, cut it.

Apply every fix to `report.md` directly with the edit tool. This is a remediation pass, not a fresh research round — no new scout research rounds, just resolving the defects the reviewers flagged. Only after every raised issue is addressed may pandoc render the HTML.

#### Pandoc Details

Use the following command to invoke `pandoc`:

```bash
pandoc -s --embed-resources --standalone --css="/home/zlare/.pi/agent/prompts/research-report.css" --toc --toc-depth=3 --metadata title="Research Report: <topic>" "<md_file>" -o "<html_file>"
```

Where:
- `<md_file>` is the absolute path to the markdown file.
- `<html_file>` is the same path with a `.html` extension instead of `.md`.
- `<topic>` is a short label for the research topic, derived from the user's query.
- `--embed-resources` inlines the CSS (and any linked assets) directly into the HTML so the sidecar is fully self-contained.
- The CSS file lives at `/home/zlare/.pi/agent/prompts/research-report.css` and applies an Everforest Light Medium theme.

### Post-render verification

After running pandoc, verify the HTML file was created:

```bash
test -f "<html_file>" && echo "ok" || echo "failed"
```

If the render failed, inform the user of the pandoc error output and the markdown file location.
